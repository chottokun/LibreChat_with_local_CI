# 日本語ファイル名処理仕様と設計リファレンス

本ドキュメントは、LibreChatと本RCE API（Custom RCE）間において、日本語等の非ASCII文字を含むファイル名がどのように文字化けやファイルシステムエラーを起こさずに安全に処理されているかの動作仕様および内部設計をまとめた技術リファレンスです。

将来の機能追加、ファイルハンドリング処理の拡張、あるいは別コンポーネントの統合時に参照すべき設計要件を定義します。

---

## 1. 統合・連携の動作仕様

システム全体における日本語ファイル名の伝播および中継の仕様は以下の通りです。

```mermaid
graph LR
    User[ブラウザ] -- 1. 資料.pdf (UTF-8) --> LC[LibreChat Server]
    LC -- 2. 原本メタデータ保持 (MongoDB) --> DB[(Database)]
    LC -- 3. 原本名 (UTF-8) で中継 --> API[FastAPI (f.filename)]
    API -- 4. そのまま書き込み --> Volume[(RCE Volume)]
    Volume -- 5. UTF-8ロケールで認識 --> Sandbox[Docker Sandbox]
```

### ① 上流（LibreChat）のメタデータ中継仕様
LibreChatサーバーは、ローカルディスク保存時の安全性を確保するためにファイルシステム上では一時的にサニライズされた名前を使用しますが、データベース（MongoDB）側には「ユーザーがアップロードしたオリジナルの日本語ファイル名」をUTF-8で保持しています。
そして、当RCE APIの `/upload` エンドポイントへファイルを転送（プロキシ）する際、**データベースから引き出したオリジナルの日本語名（UTF-8）をマルチパートリクエストの `filename` パラメータに設定して送信する設計**になっています。これにより、転送時のファイル名破壊が根本的に回避されています。

### ② 本API（FastAPI）の非サニタイズ受け入れ設計
API（FastAPI）側の `UploadFile` (内部の `python-multipart`）は、この転送されてきたマルチパートリクエストの UTF-8 ヘッダーを正確にデコードし、`f.filename` に正しい日本語名を復元します。
本APIは、受け取ったファイル名に対して強制的な英数字サニタイズ（アンダースコア `_` への強制置換など）を適用せず、`safe_filename = os.path.basename(f.filename)` で安全性を確保した上で、オリジナルの名前のままコンテナの作業用ボリュームへ配置します。

---

## 2. サンドボックス内でのUTF-8処理設計

コンテナ側で日本語ファイル名のファイルをプログラムが安全に読み書きし、一覧を取得するための設計要件です。

### ① UTF-8ロケールの強制設定
`Dockerfile.rce` で以下の環境変数を定義することで、コンテナのOSおよびPythonランタイム全体をUTF-8環境に固定しています。
```dockerfile
ENV LANG=C.UTF-8
ENV LC_ALL=C.UTF-8
ENV PYTHONUTF8=1
```
これにより、Pythonコード内で `open('資料.pdf')` のように日本語ファイル名を直接指定しても、エンコーディングエラーを起こさずにネイティブにファイルを読み書きできます。また、`japanize-matplotlib` などの日本語描画フォントとの連動も安定します。

### ② `os.listdir` を用いた一覧取得設計
ファイル一覧をAPIに返す際、コンテナ内でシェルコマンド `ls` を実行して標準出力を文字列処理する方法は、ロケールや特殊文字のエスケープによる文字化けを誘発しやすいため**厳禁**とします。
本APIでは、コンテナ内で以下のPythonインラインコードを動作させ、ファイル名のリストを厳密なJSON形式でエンコードしてAPIに引き渡す設計を採用しています。
```python
import os, json
print(json.dumps(os.listdir('/mnt/data')))
```
これにより、スペースや日本語を含むファイル名が一切崩れることなくAPIに引き渡されます。

## 3. ダウンロード時の RFC 5987 準拠設計（要件）

RCEから生成された結果ファイルをユーザーがブラウザでダウンロードする際、日本語ファイル名が文字化け（あるいはアンダースコアへの置換）を起こさずに復元されるためのHTTPヘッダー要件です。

将来、新しいファイルダウンロード用エンドポイントを実装・拡張する場合は、必ず以下の **RFC 5987 準拠** の設計を踏襲してください。

### 実装設計
標準の `Content-Disposition: attachment; filename="資料.pdf"` というヘッダー形式は、ブラウザや中間プロキシのエンコーディング解釈の違いにより高確率で文字化けを引き起こします。これを解決するため、URLエンコードされたUTF-8文字列を `filename*` パラメータで指定します。

```python
from urllib.parse import quote
from fastapi.responses import FileResponse

encoded_filename = quote(filename)
headers = {
    "Content-Disposition": f"attachment; filename*=UTF-8''{encoded_filename}"
}
return FileResponse(filepath, headers=headers)
```
*   `urllib.parse.quote` を使用して、ファイル名（例: `日本語.csv`）を `%E6%97%A5...` のように安全なパーセントエンコーディングに変換します。
*   `filename*=UTF-8''...` のプレフィックスを指定することで、ブラウザがこれを標準的なUTF-8デコードロジックで元の日本語名へと安全に復元します。

## 4. セキュリティ上の配慮（パストラバーサル対策）

日本語ファイル名のような多様な文字セットを許可する場合、ディレクトリ境界文字（`../` 等）が混入して任意のシステムファイルが上書き・奪取される **パストラバーサル（Path Traversal）脆弱性**（例: CVE-2024-11170 等）への厳重な警戒が必要です。

### 防衛要件
1.  APIのエントリポイントでファイル名を受け取った直後に、必ず `os.path.basename()` を適用し、ディレクトリ境界を強制的に除去します。
2.  IDやセッションキーに対しては、英数字およびハイフン・アンダースコアのみを許可するバリデーション関数 `sanitize_id()` を通し、ファイルパスの組み立てにおいて意図しないディレクトリ移動（`../`）が100%発生しない設計を維持してください。
